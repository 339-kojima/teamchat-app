# PR 差分レビュー

依頼者が指定した PR の差分を、設計資料・既存仕様・実装の観点から確認し、根拠のある指摘を報告する。レビュー依頼ではアプリケーションコードを変更しない。

## 手順

1. 対象リポジトリと PR 番号を確認し、`gh pr diff <番号>` で差分を取得する。接続に失敗した場合は環境の承認手順に従って再試行する。取得できなければその旨を伝え、手元にある情報だけで差分内容を断定しない。
2. 差分に含まれる設計書・仕様資料を読み、受け入れ条件や既存動作と照合する。設計に記載のない依存関係（例: `composer.json`）、設定変更、無関係なファイルの追加・編集にも注意する。ファイル名だけでなく、変更目的が説明されているか確認する。
3. 依頼者が指定した「触っていないはず」のファイルを順に確認する。まず削除行を調べ、次に追加・変更行が意図した仕様に必要か確認する。差分にないファイルも、その事実を明記する。
4. 変更内容を読み、依頼に応じて N+1、認可の置き場所と抜け道、マスアサインメント、Blade 等の出力エスケープ、CSRF、入力検証と日本語のエラー文、既存コードとの書き方の揃いを確認する。設計書とリポジトリ固有ルールも照合する。
5. 報告には差分上の根拠と行番号を付ける。PR の差分とローカルファイルが異なる場合があるため、対象ブランチや該当コミットの内容を確認し、行番号と参照先を取り違えない。

## 受け入れ判断で人が読む観点

差分に関係する項目だけを選び、設計書・既存仕様・モックアップと実際の動作を突き合わせる。自動フックや機械的な検査で判定できる整形、テストの合否、単純な規約違反はこの節の報告対象にしない。問題を見つけた場合は修正せず、直したほうがよい箇所と、利用者やデータに起きる影響を指摘する。

- **要求との一致と範囲**：変更が関連する受け入れ条件を満たすか、対象外の機能を持ち込んでいないかを見る。仕様・設計・モックアップの間に食い違いや未決事項がある場合は、推測で合否を決めず `docs/design/questions.md` の回答・判断を確認し、解消していなければ要確認として示す。
- **閲覧範囲と権限**：プライベートチャンネルが非メンバーに一覧・詳細・検索結果などから存在ごと見えないかを確認する。作成者だけのチャンネル管理、作成者を外せない制約、投稿者本人だけの編集・削除、各操作でのサーバー側認可を確認する。画面で操作を隠すだけの制御は十分とみなさない。
- **投稿・返信の意味と保持**：メッセージと返信が古い順に並ぶか、返信が1段に保たれるか、削除済み親への返信が続けられるかを見る。投稿削除で本文を消去しつつ投稿者・日時・参照・返信を保つこと、編集済み表示が残ること、チャンネル削除ではチャンネル内の投稿・返信も削除することを設計に照らして確認する。
- **検索と公開APIの境界**：検索がログイン必須で、閲覧可能なチャンネルの投稿本文・返信本文だけを部分一致検索し、削除済み投稿を除外するかを見る。公開APIは認証なしの読み取り専用で、公開チャンネルと未削除投稿だけを返し、非公開チャンネルと存在しないIDを同じ404にするか、削除済み親への返信の `parent_id` を保つかを確認する。
- **画面の状態と入力の扱い**：画面を変える差分では、該当するモックアップと `screens.md` に照らして項目、文言、遷移、空・エラー・削除済みなどの状態を確認する。必須値の空白・改行だけの入力や上限値がサーバー側でも扱われるか、成功後の遷移が設計どおりかを見る。
- **データ変更と再実行の影響**：スキーマ変更、チャンネル削除、シーダー変更では、既存データや利用者が追加したデータへの影響を `data.md` と確定仕様に照らして確認する。シーダー再実行で初期データを所定状態に戻しつつ利用者データを消さないこと、ローカル認証情報や実利用者データを持ち込まないことを見る。
- **設計との同期と変更理由**：画面・データ・権限・API・処理・受け入れ条件に影響する実装変更に対応する設計更新があるか確認する。設計書にない依存関係、設定、無関係な変更は、差分から必要性が分からない場合にその理由を要確認として示す。

## 判定と報告

- 依頼者が判定語を指定したらそれを使う。指定がなければ「要確認」「OK」「対象外」を使う。確認材料が足りない場合は「要確認」とし、不足している情報を具体的に書く。
- 指定された列順・報告順・対象ファイルを守る。表形式を指定されていない場合、1観点につき1行で `観点 / 判定 / ファイル名:行番号 / 気づいたこと` の形式を使う。
- 不具合と断定できない設計外変更や一貫性の懸念は、確認できた事実と判断できない理由を分けて「要確認」とする。
- 依頼された場合、最後に人が自分の目で読むべき場所を優先順で最大3つ挙げる。
- 依頼されていないテスト実行、コード修正、PR への書き込みは行わない。
